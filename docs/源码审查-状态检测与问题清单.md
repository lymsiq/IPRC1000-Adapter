> 审查对象：`iprc1000_native`（Rust，`Cargo.toml` version = **0.4.36**）
> 审查时间：2026-11-06 10:35
> 审查方式：静态读码（全量 `src/`）+ 本机现场只读实测（未改动任何代码/配置）
> 背景：v0.4.36 新增 `src/hid_reader.rs`（HID 直读消费者），需要确认「状态检测」落在哪、是否有出口、文档是否同步。

## 0. 结论摘要

| # | 结论 | 严重度 |
|---|---|---|
| 1 | 界面「● 遥控器在线」**不代表按键通道可用**。它的数据源是 ETW 回调被调用的时刻，任何 BTHPORT 链路层事件都会刷新（实测 ~2 次/秒恒定），所以必然显示"在线" | **P0** |
| 2 | 新增的 HID 消费者有 3 个诊断计数器（`REPORTS/REOPENED/MISS`），**全项目零读取**：不进日志、不进 `bridge-stats.json`、不进界面 —— 现场无法判断"没反应"是哪一层断的 | **P0** |

| 6 | HID 直读与 ETW 各有一套报文解码，同一设备会产出两种 usage 集合 | P1 |
| 7 | 三份关键文档全部滞后：`VERSION.md` 写 0.4.11、`docs/原生版SOP.md` 写适用 v0.4.32 且没有 `--hid-probe`、根 `CHANGELOG.md` 只有 C# 版 1.2.x | P1 |

## 1. 「状态检测」在哪访问（直接答案）

### 1.1 现在有三条**互不相干**的检测链路

| 链路 | 入口 | 实现 | 数据源 | 能不能代表"按键可用" |
|---|---|---|---|---|
| **A. 界面在线状态** | 界面右上角 `● 遥控器在线 / ○ 遥控器休眠` | `ui_egui.rs:220` → `main.rs:56 is_online()` → `backend.rs:3467` | `Stats.last_event_ms`（**任何** ETW 回调，含链路保活） | ❌ 不能。只证明 ETW 消费者线程活着 |

## 2. 问题清单

### P0-1 「在线」判据错误，必然假在线

- 位置：`backend.rs:3036`、`3467`；`ui_egui.rs:219`
- 现象：遥控器休眠、按键完全不通时，界面仍显示"● 遥控器在线"。原因见 1.2。
- 影响：用户与客服都以这行为唯一判据，导致"显示在线但没反应"被误判成软件 bug；也掩盖了 0.4.36 之前 HID 中断通道没建立的那类故障。
- 建议：拆成两个状态，UI 分别显示。

```rust
// backend.rs Snapshot 增加
pub link_online: bool,   // 原 online：30s 内有任意 ETW 事件（链路活着）
pub key_online: bool,    // 30s 内有过按键报告（HID 直读 或 ETW 的 hid_reports）

// snapshot()
let hid_age = /* REPORTS 变化时间，需在 hid_reader 里维护 last_report_ms */;
key_online: (key_age != u64::MAX && key_age < 30_000) || hid_age < 30_000,
```

界面建议：`● 遥控器在线` 只在 `key_online` 为真时显示；`link_online && !key_online` 显示 `◐ 已连接，但按键通道未就绪（点「检测」）`。

### P0-2 HID 消费者的状态完全不可观测

- 位置：`hid_reader.rs:62-66 / 233`，`backend.rs:2860`（统计 JSON 无相关字段）
- 影响：`hid_reader` 是 0.4.36 为解决"按键收不到"新加的核心模块，但它成功与否在现场**没有任何可读出口**。排查只能靠 `--hid-probe` 手工试一次。
- 建议（三处，改动很小）：

```rust
// ① backend.rs 统计 JSON 增加字段
"\"hidReports\":{},\"hidKeyEvents\":{},\"hidOpen\":{},\"hidMiss\":{},",
s.hid_reports, s.key_events,
crate::hid_reader::REOPENED.load(Ordering::Relaxed),
crate::hid_reader::MISS.load(Ordering::Relaxed),

// ② backend.rs:3488 汇总行追加
"[i] … HID消费者: 打开 {} 次 · 读到 {} 条 · 枚举落空 {} 轮"

// ③ hid_reader.rs 每次成功打开/首次读到报告时写一行 log（已有一条，补计数即可）
```

顺带解决"0 条接口算不算故障"的判读问题：`hidOpen > 0` 说明接口存在过、句柄打开过；`hidMiss` 持续增长而 `hidOpen == 0` 才是真的没醒/没枚举到。

### P0-3 注释承诺的"键盘类检查"不存在

- 位置：`hid_reader.rs:26-31`（模块文档）vs 全文实现
- 文档原文：

  > "本模块启动时会检查设备是不是还挂在键盘类下，是的话只打一行提醒，不做额外动作"

- 实际：`hid_reader.rs` 里没有任何 `Keyboard` / `remote_still_keyboard` 调用；`main.rs:602 hid_reader::start()` 无条件启动。
- 后果（未改造机器）：`kbdhid` 与本程序**同时**读同一份报告 → 一边打字母、一边注入动作，即"双触发"，且没有任何提示。
- 建议：

```rust
// hid_reader::start() 开头
if crate::device_probe::remote_still_keyboard() == Some(true) {
    eprintln!("[HID] ⚠ 遥控器仍是键盘：按键会一边打字母一边执行映射，请先在「环境与安装」点 ④ 改造");
}
```

### P1-1 `--hid-probe` 文案错误，0 值会误导

- 位置：`hid_reader.rs:257-262`
- 现在输出 `HID 接口总数（含遥控器的）：0`，但 `paths` 已被 `VID&00020A5C` 过滤，实际是"匹配到遥控器的接口数"。
- 现场会理解成"这台机器一个 HID 设备都没有"，从而否定整个方向。建议改成：

```rust
println!("匹配到遥控器的 HID 接口：{} 个（全系统 HID 接口另外枚举）", paths.len());
```

并同时打印全量接口数与过滤前的样本（各前 5 条），便于判断是"没醒"还是"VID 过滤不匹配"。

### P1-2 打开失败日志不节流

- 位置：`hid_reader.rs:203`
- 设备存在但句柄打不开（phantom 边缘、权限、独占）时，500 ms 一轮 → 每分钟 120 行。建议照 `MISS` 的写法按次数取模，或只在错误码变化时打。

### P1-3 两套报文解码，语义不一致

- `report.rs`：`key_set()` / `diff()`（ETW 路径用，输入是 `acl[8..14]`，**不含修饰键字节**）
- `hid_reader.rs:129 decode()`：自己解 8 字节，遇到修饰位展开成 `0xE0+i`（**含修饰键**）
- 后果：同一台设备，走 HID 直读时可能产出 `0xE0..0xE7` 这类 ETW 路径永远不会出现的 usage；`keymap` 对这些 usage 无名称，日志会出现 `未知按键`。
- 建议：把 `decode` 提到 `report.rs`（`pub fn from_report_bytes(&[u8]) -> Vec<u8>`），两条路径共用；修饰键的展开策略只保留一处决策（建议与 ETW 路径一致：**不展开**，因为真机的语音键是 usage `0x10`，不是修饰键）。

### P1-4 阻塞 `ReadFile` 无超时、无取消

- 位置：`hid_reader.rs:216-237`
- 句柄是同步打开（未带 `FILE_FLAG_OVERLAPPED`），`ReadFile` 阻塞。若设备休眠但句柄未失效（Windows 蓝牙 HID 常见），线程会永久停在 `ReadFile`，之后既不会重连也不会记录任何状态。
- 建议：`CreateFileW` 加 `FILE_FLAG_OVERLAPPED`，用 `WaitForSingleObject` + 3~5 s 超时轮询；超时后 `CancelIoEx` 并重新枚举。（或退一步：定期 `HidD_GetFeature` 探活。）

### P1-5 接口过滤只认 `VID&00020A5C`

- 位置：`hid_reader.rs:120-122`（`to_uppercase().contains("VID&00020A5C") || contains("VID_00020A5C")`）
- 接口路径里的 VID 写法随栈/驱动变化（`VID&00020a5c`、`VID_0A5C`、`vid_00020a5c`）。已见到两种，但都不匹配"0A5C 不带前导 0002"的形式。
- 建议：改为 `let u = path.to_uppercase(); u.contains("0A5C") && u.contains("8502")`，或按 `BTHENUM\…VID&00020A5C_PID&8502` 父节点反查子接口（最稳）。

### P2-1 改造状态与消费者启动没有联动

- `remote_is_keyboard == Some(true)` 时消费者仍启动（见 P0-3）；`None`（未连接）时也不提示。建议启动时统一落一条 `[HID] 改造状态=已改造/仍是键盘/未知`。

### P2-2 Win32 版没有"在线"指示

- `ui_win32.rs:354-366` 的状态条只有 `声卡/麦克风/键盘驱动/遥控器`，其中"遥控器"= `remote_is_keyboard == Some(false)`（改造状态），**不是在线状态**；`is_online()` 在 Win32 版无调用点。
- 后果：两个发行版对同一故障的呈现不同，客服话术无法统一。

## 6. 复测步骤（改完后验 HID 消费者是否真的生效）

1. 唤醒遥控器（按任意键），立刻执行 `IPRC1000-Native.exe --hid-probe`，应输出 `可打开 ✓ \\?\hid#{…VID&00020a5c…}`
2. 启动主程序，`native.log` 应出现 `[HID] 已打开遥控器输入管道`
3. 连按 5 下方向键，`bridge-stats.json` 的 `hidReports`（改后为 HID 来源）与 `keyEvents` 同时增长
4. 放置 60 秒不管，再看一次：`hidOpen` 不应暴涨（暴涨 = 句柄反复掉线重连），`hidMiss` 应停止增长
