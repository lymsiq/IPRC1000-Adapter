# IPRC1000 语音遥控 · 整体开发方案 v1

> 编制：2026-11-06　｜　基线：`iprc1000_native` v0.4.46（Rust）+ `iprc1000_gui_dotnet`（C#）
> 目标：把两边的优点合成一个**可外部化配置、多机多系统多人可用**的原生 Windows 应用

---

## 0. 现状：两份代码，各有短板

| | C# 版（`iprc1000_gui_dotnet`） | Rust 原生版（`iprc1000_native`） |
|---|---|---|
| 功能完整度 | **高**：输入法档位、宏、文本动作、鼠标模式 | 中：按键/语音/注入/宏有，**无输入法档位** |
| 性能 | 一般（WinForms + WebView2，457 MB / 674 ms） | **好**（5.7 MB / 无 WebView） |
| 结构 | 散（Backend.cs 单文件 1000+ 行） | 更散（`backend.rs` 承担 ETW+注入+租约+音频+鼠标） |
| 硬编码 | 输入法快捷键写死 `0xA5` / `0xA2+0x5B` | 设备 VID/PID 写死、超时常量散落 |
| 配置 | `keymap.json` + `settings.json`，有 schemaVersion | `native.json`，字段少 |

**结论**：以 Rust 版为骨架（性能 + 无依赖），把 C# 版的**配置模型与输入法适配**移植过来，同时拆掉 `backend.rs` 这个巨石。

## 1. 需求 → 决策

| 需求 | 决策 | 理由 |
|---|---|---|
| 豆包 / 微信两种输入法 | **输入法档位（ImeProfile）外部化**，快捷键写在配置里 | 两家的语音快捷键不同（`0xA5` vs `0xA2+0x5B`），且会随版本变；写死在代码里每换版本就要改程序 |
| 按住说话 / 点按一次 | **触发模式成为配置项** `trigger = "hold" \| "tap"` | 已实现，保持 |
| Windows 按键映射 + 组合键 | 映射引擎支持 `Chord`（多键同按）与 `Sequence`（先后） | 现有只支持单键；组合键要能表达"Ctrl+C"和"先按A再按B" |
| 多机器 | **设备识别规则表**（不写死 VID/PID），机器级配置覆盖 | 换遥控器型号/换适配器不再改代码 |
| 多配置 | **profile 分层**：内置默认 < 机器级 < 用户 profile | 一套程序，多套行为 |
| 多系统 | 同上，机器级配置记录**适配器/端点名/路径**差异 | 已知差异：Intel AX200 vs Realtek 8821CE、`CABLE Input` vs `CABLE In 16 Ch` |
| 多人使用 | **按 Windows 用户隔离 profile + 数据目录** | 同机多账户各自独立 |
| 避免硬编码 | 所有魔数进 `defaults.toml`，代码里只留**语义名** | 代码读 `cfg.voice.pause_ms`，不是 `3000` |

## 2. 架构：分层 + 端口适配器

```
┌─────────────────────────────────────────────┐
│ ui/            egui 界面（只读快照 + 发命令）  │
├─────────────────────────────────────────────┤
│ app/           用例编排：启动/切换profile/自检 │
├─────────────────────────────────────────────┤
│ domain/        纯逻辑，零 Windows API         │
│   keymap      映射解析（Chord/Sequence）      │
│   device      设备身份匹配（规则表）           │
│   voice       语音租约                        │
│   macro       宏执行计划                      │
│   config      分层覆盖 + 迁移                 │
├─────────────────────────────────────────────┤
│ ports/         接口（trait），domain 只依赖它  │
│   KeySource  AudioSource  Injector  ImeSwitcher│
├─────────────────────────────────────────────┤
│ adapters/win/  唯一允许出现 unsafe/winapi 的层 │
│   rawinput  etw  winuhid  sendinput  wasapi  │
└─────────────────────────────────────────────┘
```

**铁律**：`domain/` 不 `use windows`。所有平台调用从 `ports/` 注入 —— 这是"换机器不改逻辑"的结构保证。

### 2.6 UI 技术选型（已定）

**结论：Rust + egui，继续用，不换。**

| 候选 | 体积 | 启动 | 内存 | 界面能力 | 依赖 | 结论 |
|---|---|---|---|---|---|---|
| **egui** | **5.7 MB** | **~50 ms** | **~120 MB** | 中（够用） | **零** | **选它** |
| Tauri + WebView2 | ~9 MB | ~150 ms | ~300 MB | 强 | WebView2 运行时 | 备选 |
| WinForms + WebView2（C# 版） | 3.8 MB + .NET | **674 ms** | **457 MB** | 强 | .NET 8 + WebView2 | **淘汰（已实测）** |
| WinUI 3 | 大 | 慢 | 高 | 强 | .NET + Windows App SDK | 不选 |

**为什么是 egui**

1. **核心痛点不是界面，是通道稳定性**——今天一整天都耗在设备/驱动/端点，UI 从没成为瓶颈。换 UI 框架是负收益。
2. **零依赖单 exe**。客户机上已经要装 WinUHid 驱动、VB-CABLE 声卡；再叠一个 WebView2 运行时是给自己加变量（C# 版就吃过白屏事故）。
3. **实测数据支持**：C# 版 WebView2 占启动 674 ms 里的 341 ms（51%）、内存 457 MB 里的 356 MB。egui 版 50 ms / 120 MB。

**egui 需要自己补的三件事**（都在 P0/P1 内）

| 需求 | 做法 | 量级 |
|---|---|---|
| 中文字体 | 加载 `C:/Windows/Fonts/msyhl.ttc` | 已做 |
| 应用条拖动排序 | `Sense::drag()` + 手写索引交换 | ~80 行 |
| 按键实物图 + 热区 | `egui::Image` + 归一化坐标表（配置化，不写死像素） | ~120 行 |

**什么时候才该换**

只有两条同时成立才考虑 Tauri：

- 需要**像素级还原设计稿**（品牌一致性要求）
- 需要**同一套 UI 跑在浏览器里**（Web 端复用）

即使成立，也要接受 **+100 ms 启动、+180 MB 内存、双进程调试**。现在不成立。

## 3. 模块划分

| 模块 | 职责 | 对外契约 | 现有代码来源 |
|---|---|---|---|
| `config` | 三层合并、schemaVersion 迁移、热加载 | `Config::load() -> Config` | `settings.rs` 扩写 |
| `keymap` | 绑定解析、Chord/Sequence、多组 | `resolve(usage, profile) -> Action` | `keymap.rs` + C# `Keymaps.cs` |
| `device` | 设备身份匹配（规则表驱动） | `identify(desc) -> Option<DeviceId>` | `device_probe.rs` 重写 |
| `input.key` | 按键通道（Raw Input 主 / ETW 辅） | `KeySource::next()` | `hid_reader.rs` + `backend.rs` 拆 |
| `input.audio` | 音频帧、抖动缓冲、重采样 | `AudioSource::next_frame()` | `backend.rs` 拆 |
| `inject` | WinUHid 优先、SendInput 回退 | `Injector::send(&[vk])` | `winuhid.rs` |
| `ime` | **输入法档位**：检测、快捷键、端点检查 | `ImeSwitcher::profile()` / `trigger_voice()` | **需从 C# 移植** |
| `voice` | 语音租约（不动） | `arm/disarm/reconcile` | `backend.rs` 原样搬 |
| `macro` | 宏/文本/录制 | `MacroEngine::run()` | `backend.rs` + C# |
| `platform` | 路径、注册表、UAC、日志 | — | `paths.rs` 扩写 |
| `diag` | 快照、自检、报告 | `snapshot() -> Report` | `snapshot.ps1` 移植为 Rust |
| `ui` | 状态栏、环境页、配置页 | — | `ui_egui.rs` |

`backend.rs` 拆成 `input.{key,audio}` + `voice` + `macro` + `app`，**目标单文件 ≤ 600 行**。

## 4. 关键数据结构

### 4.1 设备身份（去硬编码的关键）

```toml
# config/devices.toml
[[device]]
id        = "iprc1000"
label     = "IPRC1000 遥控器"
tlc       = "0x01/0x06"                     # 键盘集合
match_all = ["hid_vid:0A5C", "hid_pid:8502"] # 全部满足
match_any = ["name~IPRC", "name~Broadcom Bluetooth Wireless"]
```

代码里只认 `DeviceId("iprc1000")`。**换型号只改 toml，不动代码**。

### 4.2 键位绑定

```toml
[profile.default.bindings]
navigate_up   = { type = "key", vk = "VK_UP" }
copy          = { type = "chord", keys = ["VK_CONTROL", "VK_C"] }
open_menu     = { type = "sequence", keys = ["VK_APPS", "VK_DOWN"] }
voice         = { type = "voice", mode = "hold" }        # 走语音租约
volume_up     = { type = "media", code = 0xAF }
text_hello    = { type = "text", slot = 1 }
macro_demo    = { type = "macro", id = "demo" }
```

- `chord` = 同时按下（注入侧分两帧）
- `sequence` = 按顺序（间隔可配）
- 负数哨兵（`-1..-4` 鼠标动作）保留兼容，但**新配置用命名类型**

### 4.3 配置分层

```
%APPDATA%\IPRC1000 Adapter\
  config\
    machine.toml        机器级：适配器名、音频端点、按键通道偏好、传感器存在性
  profiles\
    default.toml        用户配置组（含 bindings）
    mouse.toml
  voices\
    ...
  logs\  wav\
<安装目录>\config\
  defaults.toml         出厂默认（随包发，只读）
```

**合并顺序**：`defaults.toml` → `machine.toml` → `profiles\<active>.toml`
每一层记录来源，界面能显示"这个值来自哪一层"（避免"改了没生效"的经典困惑）。

### 4.4 输入法档位（C# 版已有，Rust 版缺）

```toml
# defaults.toml
[ime.doubao]
label         = "豆包输入法"
detect_reg    = "HKCU\\Software\\ByteDance\\DoubaoIME"
voice_hotkey  = ["0xA5"]              # 单个虚拟键
[ime.wechat]
label         = "微信输入法"
detect_reg    = "HKCU\\Software\\Tencent\\WeChatIME"
voice_hotkey  = ["0xA2", "0x5B"]      # Ctrl+[？按 C# 版实测序列
```

**为什么要外部化**：这两个键值是**输入法版本相关**的，写死过一次就踩过（C# 版 `Backend.cs:745`）。放进 toml，用户/客服改配置即可。

## 6. 重构怎么做（从 v0.4.46 到现在这套架构）

**用绞杀者模式（Strangler），不推倒重来** —— 每一步都能单独发版、单独回滚。

### R0 · 冻结基线（半天）

1. 打 tag `v0.4.46-baseline`
2. 两台机器各跑一次 `snapshot.ps1`，存进 `handoff/`
3. 记录当前 `keyEvents` / `frames` / `seqLost` 作为对照

**没有基线就不许动结构** —— 否则改完无法判断是变好还是变坏。

### R1 · 配置外部化（3 天）★ 收益最大的一步

**做法**：新增 `config` 模块，**先读 toml，读不到回落旧 JSON**。

```
settings.rs  →  保留，标记 deprecated
config.rs    →  新增，三层合并
```

- 把 `settings.rs` 的字段逐个映射到 `defaults.toml`
- 把 `keymap` 的默认值从 `keymap.rs` 的 `Defaults` 搬到 `defaults.toml`
- 首次启动自动 dump 一份 `defaults.toml` 到 `%APPDATA%`

**回滚点**：删 `config.toml` 即回落旧逻辑。

### R2 · 拆 `backend.rs`（5 天）

按**依赖方向**拆，不按行数拆：

```
backend.rs（约 3200 行）
├── voice.rs        租约（整块搬，不改一行逻辑）     ~150 行
├── input_key.rs    Raw Input 消费者 + 认领          ~600 行
├── input_audio.rs  ETW 解码 + 抖动缓冲 + 重采样      ~800 行
├── macro_engine.rs 宏/文本/录制                     ~700 行
└── app.rs          编排（启动顺序、profile 切换）    ~400 行
```

**顺序**：先搬 `voice`（最独立、最不能改），再搬 `input_audio`，最后拆 `input_key`。

**每个 crate 搬完立即跑一次协议 C/E 组**，不对就回退。

### R3 · 设备识别去硬编码（2 天）

`device_probe.rs` 现在把 `VID_0A5C` / `PID_8502` 写在匹配函数里。改成：

```rust
fn identify(desc: &DeviceDesc, rules: &[DeviceRule]) -> Option<&DeviceId> {
    rules.iter().find(|r| r.matches(desc)).map(|r| &r.id)
}
```

配 `devices.toml`（见 §4.1）。**验收**：把 `defaults.toml` 里 `match_all` 改成故意写错，程序必须报"未匹配"，而不是假装正常。

### R4 · 移植输入法档位（3 天）

原生版**完全没有**这一层。从 C# `Backend.cs:711-760` 移植：

1. `ImeDetected()`：扫注册表判断装了哪个
2. `EnsureImeProfileApplied()`：把档位的快捷键映射成遥控器按键
3. 端点检查：`CABLE Output` 是否默认录音设备

**验收**：两个输入法各录一段语音，都能出字。

### R5 · 删除旧路径（1 天）

- 删 `settings.rs`（或标记 only-for-migration）
- 删 `backend.rs` 空壳
- 删 `keymap.rs` 里的 `Defaults` 硬编码（改读 toml）

**验收**：`cargo clippy` 0 警告；`--selftest` 全绿；协议全过。

### 6.6 按周排期（7 周）

| 周 | 动作 | 产出 | 回滚点 |
|---|---|---|---|
| **W1** | R0 基线 + R1-1 `config` crate（读 toml、回落 JSON） | 启动时自动 dump `defaults.toml`；删掉它仍能跑 | 删 toml |
| **W2** | R1-2 keymap 默认值搬进 toml + 界面标注"值来自哪层" | 改 toml 立即生效 | 删 toml |
| **W3** | R2-1 `voice` 整块搬（**不改一行逻辑**）+ R2-2 `input_audio` | 协议 E 组通过 | `git revert` |
| **W4** | R2-3 `input_key` + R2-4 `macro_engine` / `app` | 协议 B/C 组通过，`backend.rs` ≤ 100 行 | `git revert` |
| **W5** | R3 设备识别规则表（`devices.toml`） | 改规则不改代码；规则写错时明确报"未匹配" | 保留旧匹配作 fallback |
| **W6** | R4 移植输入法档位（豆包 / 微信） | 两种输入法各端到端出一段字 | 配置项可关闭 |
| **W7** | R5 删旧路径 + `clippy` 0 警告 | **v0.5.0** | 打 tag |

**两条铁律**：

1. **每一步单独发版**（0.4.47 → 0.4.48 → …），不许攒成一个"大重构"再发。今天的教训够深了：一次改太多，出问题分不清是谁的锅。
2. **每个版本都要在两台机器上跑一遍协议对应组**，一台不算。

## 7. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 改设备识别后认不到遥控器 | **高** | 按键全无 | 保留"旧匹配逻辑"作 fallback，配置里可 `match_any`；先加规则表再删旧路径 |
| 拆 `backend.rs` 拆丢语音租约的续租点 | 中 | 语音卡键 | 租约整块搬，**不注释、不改条件**；搬完先跑 E 组 |
| 配置迁移丢用户键位 | 中 | 用户投诉 | 迁移前 `.bak` 备份；迁移后逐字段比对日志 |
| 输入法快捷键因版本失效 | **高** | 语音不能用 | 已外部化，客服改 toml；界面显示"当前档位快捷键" |
| 多人共用一台机器配置串 | 中 | 互相覆盖 | 数据目录按 `SID` 隔离，不共用 `%APPDATA%` 根 |
| Program Files 只读导致写配置失败 | 中 | 启动即崩 | 配置一律写 `%APPDATA%`，程序目录只放 `defaults.toml` |

## 8. 验收要点（对齐《测试协议 v1》）

| 阶段 | 必过 |
|---|---|
| P0 | 删配置能自愈；三层覆盖顺序正确 |

## 10. 附录：从 MoteDeck 抄什么、不抄什么

> 参考对象：`HZDavy/MoteDeck` v0.1.11（2026-11-04），**GPL-3.0**，Python 3.12，174 MB
> **只抄设计与数据结构，不拷一行代码**（GPL-3.0 有传染性，本仓库是私有）

### 10.1 三样值得抄

#### A. 单击 / 双击 / 长按 三动作

```toml
[profile.default.gestures.ok]
tap        = { type = "key", vk = "VK_RETURN" }
double_tap = { type = "key", vk = "VK_APPS" }
long_press = { type = "macro", id = "menu" }
```

判定规则（**延迟优化的关键**）：

```
按下 → 记 t_down
  ├─ 按住 ≥ LONG_PRESS(550ms) 且该键配了 long_press → 立即触发，标记 consumed
  ├─ 抬起时已 consumed → 什么都不做
  ├─ 抬起 → 若该键没配 double_tap → **立即触发 tap**
  └─ 抬起 → 若配了 double_tap → 起 DOUBLE_WINDOW(300ms) 定时器
         ├─ 窗口内又来一次按下/抬起 → double_tap
         └─ 窗口到期 → tap
```

**不要对所有键统一延迟 300 ms**——只有**配了 `double_tap` 的键**才等窗口。否则方向键会明显发粘（MoteDeck 也是这么做的，README 说"长按动作只触发一次；允许连续执行的普通动作在持续按住时会重复"，即未配置手势的键走直通路径）。

三个数放 `defaults.toml`：

```toml
[gesture]
long_press_ms   = 550
double_window_ms = 300
repeat_hold     = true      # 未配手势的键按住时重复
```

#### B. 按前台应用切档案

```toml
# profiles/default.toml
[[app_profile]]
match  = "chrome.exe"        # 前台进程名，不区分大小写、精确匹配
label  = "Chrome"
bindings = { navigate_up = { type = "key", vk = "VK_PRIOR" } }

[[app_profile]]
match  = "vlc.exe"
bindings = { ok = { type = "key", vk = "VK_SPACE" } }
```

**四条必须照做的规则**：

1. **只存覆盖项** —— 档案里没写的键，运行时**回落全局**。这样改全局映射能同时影响所有应用。
2. **匹配用前台进程名**，不区分大小写的**精确**匹配（不用前缀/通配，避免 `chrome.exe` 误匹配 `chromedriver.exe`）。
3. **只切按键映射**，默认**不动语音和音频设置**（否则切个应用麦克风就换了，很吓人）。
4. **档案库独立文件** `app_profiles.toml`，带 `version` 字段。读旧版本 → 原子迁移（写新文件 → 成功再删旧 → 旧文件留 `.bak`）。

运行时判定：每 500 ms 查一次前台进程（`GetForegroundWindow` + `GetWindowThreadProcessId` + 查进程名），**变化时才切换**。不要挂在按键事件里查——那会把每次按键都拖慢。

#### C. 整体配置导出 / 导入

```toml
# export-20261106.toml
[meta]
version   = 1
app       = "IPRC1000"
created   = "2026-11-06T17:30:00+08:00"
machine   = "PC-20260728LQXO"     # 仅记录，导入时不校验

[global]          # = 当前 profile 的 bindings 与手势
...
[[app_profile]]
...
```

规则：

- **导出包含**：全局映射 + 全部应用档案 + 手势配置
- **导出不含**：设备身份、配对信息、语音档位、音频端点（这些是机器相关的，跨机器导入只会带来错配）
- **导入策略**：替换全局与全部档案；重名档案自动加序号，**不覆盖已有**
- **导出位置由用户选**，但**禁止写入程序数据目录**（否则和自动保存打架）

### 10.2 三样不能抄（IPRC1000 与小米遥控器的硬件差异）

| 层 | MoteDeck 的做法 | 为什么对 IPRC1000 无效 | 我们必须自己做 |
|---|---|---|---|
| **按键读取** | `hid_helper` 直读 HID 接口 + UAC 提权 | IPRC1000 是 **`kbd` 顶层集合**，ACL **SYSTEM-only**，管理员也是 `err=5`（实测 60 次全失败） | **Raw Input**（`RIDEV_INPUTSINK` 隐藏窗口）+ **ETW 兜底** |
| **语音采集** | 把遥控器当**系统标准蓝牙麦克风**（HFP/A2DP），取 `CABLE Output` 对应端点 | IPRC1000 音频走 **BthPort 私有 ACL 帧**（653 B/帧，HID 中断通道），**Windows 不把它当录音设备** | **ETW 解析 ACL → 抖动缓冲 → 重采样 → CABLE** |
| **语音结束判定** | 小米有可靠的松手事件，不需要额外机制 | IPRC1000 **按住期间零报文**、固件 30 s 自动收工**有时不发松手报文** | **语音租约**（见 `docs/语音租约设计.md`） |

这三层正是我们已投入最多、也最不能被替换的部分。**MoteDeck 的"下半身"对这块硬件完全不适用**，只有"上半身"（UI + 映射 + 注入）可复用。

### 10.3 一句话结论

```
抄它的 UI 语义与数据结构（手势 / 应用档案 / 导入导出），
保留我们的 Rust 内核（Raw Input + ETW + 租约），
不 fork、不引入 Python、不碰 GPL。
```
