## 1. 启动时间轴（`webview.log` 的 `[T+xxx ms]`）

基准取**进程真实创建时刻**（`Process.StartTime`）。用进程内 `static Stopwatch` 会因
**静态字段惰性初始化**把开头整段抹掉（实测首行显示 `T+0 ms`，而那时进程已跑了 135 ms）。

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 进程创建 → CLR + WinForms 初始化完成 | 135 ms | 20% |
| 窗口构造（KeyFilter / Backend / 托盘 / WebView2 控件） | 135 ms | 20% |
| Load + 键盘钩子 + RAW INPUT | 8 ms | 1% |
| BeginInvoke 消息循环往返 | 52 ms | 8% |
| **WebView2 环境创建（Chromium 起进程）** | **341 ms** | **51%** |
| 导航已发起 | 3 ms | — |
| 合计 | **674 ms** | 100% |

- **「环境就绪」≠「页面渲染完成」**：`Navigate()` 只**发起**导航，返回时页面还没渲染。
  v1.1.2 起 `NavigationCompleted` 常开打点「页面渲染完成」——那一行才代表用户看到内容。
- 那 52 ms 的 BeginInvoke 往返**是故意的**：不那样做，WebView2 初始化会阻塞 `Load`，
  窗口要晚 340 ms 才画出来。

### 实测否定掉的优化（别重试）

| 方案 | 结果 |
|---|---|
| `PublishReadyToRun` | **反而慢 15 ms**（674→689）。exe 2.55→4.06 MB，「WinForms 初始化」135→152 ms，读大镜像的成本盖过省下的 JIT |
| `PublishTrimmed` | `error NETSDK1175` —— 启用剪裁不支持 Windows 窗体。**WinForms 是裁剪的硬阻塞** |
| 换 Rust / Tauri 2 宿主 | 省约 40–57 MB 内存（10%），**WebView2 的 356 MB 一分不少**（Tauri 在 Windows 上就用 WebView2）；启动那 341 ms 也照样付 |
| 提速 ETW 填缓冲（冷 200ms→10ms） | **形态不对**，解不了首包延迟问题（见 §3）|
| WebView2 用户数据目录膨胀 | 74.6 MB / 338 文件，正常范围，不是原因 |

### 沙箱里能测什么 / 不能测什么

我启动的实例 **WebView2 环境能起来、导航能发起**，但**页面不渲染** →
`NavigationCompleted` 与前端 JS 都不触发（`--selftest` 也因此恒走 18 s 兜底）。
所以「页面多久出来」「Dispose 后 Chromium 进程是否真退出」「托盘态内存」
**只能由用户在真机读 `webview.log` / 任务管理器确认**。

## 2. 内存构成与 UI 选型

| 组成 | 占用 | 占比 |
|---|---|---|

⚠ 机器上常另有 ~370 MB `msedgewebview2`，父进程是 **SearchHost（Windows 搜索）**，别算进来。

| 方案 | 托盘态 | 打开窗口 | 视觉 |
|---|---|---|---|

| 原生 WinForms（`--native-ui`） | ~102 MB | ~102 MB | 降级，已做完、默认不启用 |

**UI 框架选型**（同规模骨架：3 页 / 4 卡片 / 35 按钮 / 23 行）：

| 框架 | 空窗口基线 | 完整界面 | 结论 |
|---|---|---|---|
| WPF 8 | **139.4 MB** | 139.4 MB | **淘汰** —— 固定开销是 WinForms 的 2.7 倍 |
| WinForms 8 | **50.3 MB** | **54.3 MB** | **选它** —— 控件几乎不花钱（+4 MB）|

## 3. 「录音中断」= 首包 ~0.5 s（**仍然存在**，且非我们代码所能修）

> **2026-10-16 复核（v1.2.4，335 次按下）**：结论**没有变化**，而且这次拿到了
> "我们的改动碰不到它"的直接对照证据 —— 见下面第二张表。

统计「语音键按下 → 首包音频到达」（`router.log` 的 `[LAT]` 行）：

| 档位 | 次数 | 占比 | 说明 |
|---|---|---|---|
| **热 <50 ms** | 156 | **46.6%** | 取值 0~31 ms。SCO 链路还活着，一按就出声 |
| 中 50-300 ms | 20 | 6.0% | 117~154 ms —— 正是"声卡预热"耗时 |
| **冷 ≥300 ms** | 159 | **47.4%** | 强聚集**两簇**：460-479 与 520-539 |

中位 **138 ms**，十分位 `[8, 10, 14, 30, 138, 468, 519, 529, 531]` ——
**典型双峰**：要么几十毫秒，要么半秒。

### ★ 我们的改动对它没有影响（前后对照）

| | n | 中位 | <50 ms | 300-499 | 500-699 |
|---|---|---|---|---|---|
| v1.2.4 **之前** | 221 | 138 ms | 47% | 16% | 31% |
| v1.2.4 **之后** | 115 | 138 ms | 45% | 16% | 32% |

抖动缓冲、回调隔离、解析器修复 —— 一条都没能改变这个分布，**因为延迟产生在更上游**：

- 两簇紧聚（相隔 ~60 ms）**不像** ETW 填缓冲造成的（那会散成 0~200 ms 均匀分布）
  → 指向**蓝牙 SCO 链路重建的固定时序**。
- 会话内帧率 ≈50 包/s（正好实时）且**无补发突发** → 开头那段**真没产生**（不是迟到）。
- `CableRouter.cs` 明确「声卡**一直开着**，不再按静默时长自动关」→ END 不关流，
  `声卡已就绪=True` 一直成立，**中断不在声卡侧**。
- 按住期间**没有一次**会话被切成两段；默认录音设备 48/48 检查全正确。

⇒ 唯一可做的仍是：**按住后数半拍再开口**。（用户侧已经这么用了。）

### 顺带记两条 2026-10-16 的实测

1. **`未识别分片` 里绝大多数是 L2CAP 信令**（CID `0x0001`，形如 `08 00 01 00 02 02 04 00`），
   实测 86 条 / 100 分钟 —— 是建链协商用的小包，**与音频无关**。
   v1.2.5 起单独计成 `sigFrag`，不再混进"未识别"，免得看着像帧格式出了问题。
2. **`seq 跳号` 曾经误报**：12 次会话 → 12~13 次跳号、累计"跳过 1500 帧"，
   而同期 `组帧失败 = 0`（音频一帧没丢）。根因是"清序号基准"写在发 CLEAR 那一段，
   而序号比较在函数**最前面** ⇒ 每个会话的第一帧都拿上一段的 seq 去比。
   v1.2.5 改成按「距上一帧的空档 ≥ `IDLE_END_MS`」判新会话（与 CLEAR/END 同一套语义，
   且**不依赖 UDP 是否启用**）。回归用例见 `tools/bridge_loss_selftest.py` 的 ⑧。
   **假仪表比没仪表更糟** —— 它会让人去追一个不存在的故障。

### 卡键看门狗阈值（`StuckGuard.Decide()`，纯函数有单测）

**v1 是死的**（盯"遥控器多久没上报"，而那只字段只在 Raw Input 路径维护，ETW 模式下不跑）
⇒ **v2 改成盯「注入了还没放开」+ 用音频判据**。实测事实：按住语音键 30 s 期间
**遥控器上报次数 = 0**（"遥控器静默"不能当判据），但**音频帧一直在传**
⇒ **「按着 + 音频静默 > 3 s」= UP 丢了**。

| 按钮 | 阈值 |
|---|---|
| voice | 3 s 宽限后音频静默 >3 s 即放开（拿不到信号时 120 s 兜底）|
| 方向键 | **60 s**（长按滚菜单是真实用法，**不能 15 s**）|
| 其它 | 15 s |

诊断口诀：**「最近收到音频」一直涨** → 帧没来，查遥控器/蓝牙/ETW；
**帧在来但通话软件无波形** → 查 CABLE Output 之后。
丢帧要看 **`seqLost`（总账）** 配 **`lostCont`/`oddFrag`/`truncCont`（分账）**：
`oddFrag` 涨 = 分片长度变了（不是丢，是"变了"）；`truncCont` 涨 = 负载被 ETW 截断；
两者都不涨而 `seqLost` 涨 = 事件真没到（链路/ETW）。**别只看一个数就下结论。**

## 4. 分析日志的成套手法（排查时照着做）

1. **注入配对**：把 `key-events.log` 的 `INJECT DOWN/UP <VK>` 按 VK 配对，
   数量不等 = 有键没被释放。再按时间排序看 depth（>1 = 重复按下，<0 = 孤立 UP）。
2. **按住窗口 vs 桥事件**：从 `APPLY voice DOWN/UP` 取出按住区间，
   把 `bridge.log` 的「会话开始（CLEAR）/会话结束（END）」投进去 ——
   落在区间内且距按下 >1.5 s 的才是"说话中途被打断"（+0.5 s 左右是**正常开场**）。
3. **帧率对账**：`[END] 会话结束（累计 N 包）` 与上一行 `[CLEAR]` 的包数差 ÷ 会话时长
   ≈50 包/s 说明没丢；明显偏低通常是 600 ms 静默尾巴，不是空洞。
4. **首包延迟**：`router.log` 的 `[LAT] … 首包音频到达 N ms（声卡已就绪=）`，看分布形态。
5. **驱动绑定**：`Enum\HID\*0a5c*8502*\*` 下每个实例的 `Service`，`kbdhid` = 仍是键盘。
6. ⚠ **日志会被清空**（界面上有"清空日志"）：事发历史可能已经没了。
   排查结论要**当场写进本文件或 CHANGELOG**，别指望以后还能从日志里翻出来。
