## 1. 注入是「整份报告快照」模型

`WinUhidInjector.Send(vks)` 每次组一个 **8 字节完整 HID 报告**（byte0 = 修饰键位、
byte2..7 = 最多 6 个普通键），`Release()` = 发**全零报告**。

⇒ **每次 Send 都是"当前按下的全集"，会覆盖上一份报告** —— 所以"同时按住两个键"在
设备层面本来就做不到，后按的会把先按的从报告里挤掉（系统立刻认为先按的抬起了）。

**正确做法只有一个**：任何变化都按 `_heldButtons` 重算**全集**再整份下发
（`KeyFilter.InjectSet(ComputeIntended())`）。日志仍按**变化量**分别记 DOWN/UP，
所以分析脚本的格式不用改。

**组合键要分两帧**：`Send()` 在"含修饰键且不止一个键"时先发一帧只有修饰键的、
再发"修饰键 + 主键" —— 因为 `Win+X`、`Win+L` 这类系统热键判定条件要求
主键按下时修饰键**已经处于按下状态**，塞进同一帧会漏判。

**媒体键不走虚拟 HID**（键盘报告描述符表达不了 Consumer Page），走 `SendInput`，
且是点按语义、不参与"整份报告"。

## 2. 已修的卡键根因（2026-10-15，提交 `6624c7b`）

1. **`_injectedNow` 曾是单个全局槽**（不是按按键分槽）。松手时用它，而不是"这个按键
   按下时记录的那组键" → 同时按住两键时**先松的会去释放后按的那个键**，并把它自己在
   `_heldButtons` 里的登记一起删掉 ⇒ **看门狗再也看不到它，键永久卡住**。
   → 现改为 `_injectedSet`。
2. `_heldButtons` / 日志按"两个都按着"记，而设备层面已被整份报告顶掉 → 账与实际不一致。
3. **`InjectRelease` 不清 `_injectedNow`**（注释却写"已在 InjectRelease 里清"，实际没有）
   → 看门狗强制释放后仍留一组旧键，之后任意一次松手都会去放那组旧键。

**复现序列**（回归自检用的就是它）：按住 A → 再按 B → 先松 A → 再松 B。
旧实现在最后一步 A 的键**永远不会被释放**。

## 3. 现在的三道保险（缺任一道都可能再卡键，`package.py` 有断言）

| 保险 | 做法 |
|---|---|
| 整份报告下发 | `InjectSet(ComputeIntended())` —— 报告恒等于"所有按住中按钮的键并集" |
| **孤儿键回收器** | 每秒扫 `GetAsyncKeyState`：**系统说按着、我们已不持有**持续 3 秒 → 补全零报告 + 记 `stuck-guard.log`。**以系统状态为准，不问我们自己的账** —— 因为卡键的根因类别就是"账不可靠" |
| 启动兜底 | `ClearStaleModifiersOnStart()`：只对 `GetAsyncKeyState` **真的报"按着"**的修饰键补 KEYUP（清上一个实例被强杀留下的残留）。`IPRC1000_NO_START_CLEAN=1` 可关 |

**回收器为什么安全**（三条）：① 只在**我们没持有任何键**时才动手 —— 此时全零报告不可能
碰到合法按住的键；② 只在 `InjectableVks()`（本程序可能注入的键）里找，绝不碰别的键；
③ 全零报告只作用于**我们自己的虚拟键盘设备**；系统按键状态是**分设备合并**的，
所以物理键盘上按着的键**不受影响**。

**单实例保护**：每份实例都创建自己的虚拟键盘；一份在按住某键时被强杀，那个键就留在
**它那台**设备上，新实例管不到它（实测设备列表里出现过两组 `HID_DEVICE_SYSTEM_VHF`）。
第二实例改为唤起已有窗口后自己退出（实测 345 ms）。

**回归自检**：`--inject-multikey-test` —— 复现上面那串序列，
用 `GetAsyncKeyState` 读系统真实状态判 4 条断言。
⚠ **必须在真·winuhid 下跑才有意义**：退回 SendInput 时它也会"通过"，
因为 SendInput 是离散事件、没有报告快照语义（实测踩过这个"假通过"）。

## 4. `WinUHidCreateDevice` 会短暂失败（静默降级的源头）

实测：上一次实例被 `taskkill /F` 强杀后，驱动设备槽位会被**短暂占住**，
紧接着的新进程创建虚拟键盘**直接失败**（日志里连着 6 条失败），几秒后才恢复正常。

失败时整条注入链会**静默退化成 SendInput**，而 SendInput 会被输入法过滤
→ 现象是"**遥控器按了没反应**"，而旧版本日志上什么都看不出来。

**现在**：创建失败会留痕 + **后台自愈重试**（最多 6 次、逐步拉开间隔，不阻塞按键热路径）。

⇒ **排查"按了没反应"第一步就看 `key-events.log` 里有没有 `INJ` 行。**

## 5. 遥控器驱动绑定：重连后会自己退回键盘（2026-10-16 修复）

- **现象**：重连后老问题复发 —— 语音键漏 `m`、幽灵报告漏 `i`、按键重复刷屏，
  **只能靠重启程序**才会好。
- **根因**：蓝牙重连时 Windows **销毁旧的 HID 子设备实例、建一个新实例**
  （`Enum\HID\...\` 下实例后缀 `&N&` 递增，实测 `&2&` → `&4&`）。
  我们设的"非键盘"驱动绑定挂在**旧实例**上，已随实例消失；新实例重新做驱动匹配，
  可选只有 inbox INF → `keyboard.inf`（靠兼容 ID `HID_DEVICE_SYSTEM_KEYBOARD`）胜出。
- **为什么后果严重**：按键来源此时仍是 ETW，而 **ETW 模式下钩子不装**
  ⇒ `m` / `i` 直接漏进前台应用，没人拦。
- **修**：`Backend.RecheckDeviceDriver()` 每 2 秒在**探针线程**复查；
  `WM_DEVICECHANGE`（`OnDeviceMayChanged`）把它压到 ≤500 ms。两步、顺序重要：
  ① 先 `AutoSelectKeySource()` 上保护（切钩子拦截，**不依赖驱动切换成功**）；
  ② 再把驱动切回非键盘，成功后来源切回 ETW。切了没生效 → 10 分钟后退，不反复重枚举。
- ⚠ 驱动切换阻塞 1~2 秒，**只能在探针线程做**；`WndProc`（UI 线程）只置标志位。
  手动「还原为键盘」会**同时关掉**「自动切回非键盘」，否则周期复查会立刻改回去。
- **判据函数**：`Env.RemoteStillKeyboard()` = 扫 `Enum\HID` 里 VID 0a5c/PID 8502 的实例，
  有 `Service == kbdhid` 就是键盘。日志（`key-events.log`，前缀 `DEV`）记下每一次变化。
- **没采用的方案（记录理由）**：装自定义 INF 让 `input.inf` 永久胜出**不可行** ——
  只能靠**兼容 ID** 匹配，而 `HID_DEVICE_UP:0001_U:0006` 是通用键盘兼容 ID，
  等于把所有 HID 键盘都改成非键盘。应用级自愈更可控。
- **复现手法**：`tools/SetHidDriver/publish/SetHidDriver.exe --revert`
  （还原成 keyboard.inf）即可模拟回归，**不用真的断蓝牙**。

## 6. 遥控器的「幽灵报告」

遥控器的 HID 报告里会**紧跟真实按键之后约 2 ms** 出现一个 `keyboard usage = 0x0C`
（Windows 映射成 VK `0x49` = 字母 `i`）。低级钩子比 Raw Input 先拿到它，
若不管就会在输入框里不断插 `i`。

修法：只要看到遥控器任何按键，就把幽灵键位**武装 40 ms**（实测幽灵只晚 1~2 ms，
40 ms 有 20 倍余量，而人手连续两键间隔通常 80~200 ms，几乎不会误伤）。
每次真实按键释放后还会收到一对 `0x0C DOWN/UP`（同毫秒内），它不在 keymap 里，
**不会被注入**，无害。
