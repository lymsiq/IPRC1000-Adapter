# 进程拆分：边界、协议与现状

> 版本：v1.2.88（2026-10-29）｜状态：**地基已跑通并实测**，UI 转发与安装器闭环待做。

---

## 一、为什么要拆

现在是一个进程全包：窗口、WebView2、按键、注入、音频、探针。
后果：**WebView2 一崩，按键和语音全断**；同时"换宿主语言"要重写 1 万行。

拆开后：

```
┌──────────────────┐  命名管道（长度前缀帧）  ┌──────────────────────┐   UDP 31681/31680  ┌────────────┐
│  宿主（UI）       │ ◄──────────────────────► │  业务进程             │ ◄────────────────► │  Rust 桥   │
│  窗口/托盘/WebView│       命令 + 状态          │  注入/映射/音频/探针   │   按键/音频帧       │  ETW 解析  │
└──────────────────┘                          └──────────────────────┘                    └────────────┘
```

| 层 | 代码量 | 职责 | 换语言的成本 |
|---|---|---|---|
| 宿主 | ~1,332 行 | 窗口、托盘、WebView2、把 JS 命令转给业务 | **可整体替换**（含将来 Rust 重写）|
| 业务 | ~9,036 行 | 按键映射、注入、鼠标、音频、截图点击、设置、探针 | 无需改动 |
| 桥 | 1,941 行（Rust）| ETW 取帧、组帧、UDP 转发 | 已经是 Rust |

## 二、进程与入口

| 入口 | 行为 |
|---|---|
| `IPRC1000 Adapter.exe`（无参数）| **现有模式**：UI + 业务同进程（保持兼容，不改变用户可见行为）|
| `IPRC1000 Adapter.exe --headless` | **只跑业务**：不建窗口、不碰 WinForms；起看门狗、桥、音频路由，监听命名管道 |
| `IPRC1000 Adapter.exe --pipe-test <方法>` | 联调/诊断：连业务进程调一条命令并打印结果 |

单实例保护：`Global\IPRC1000Adapter.Service`（业务只允许一份，避免两个进程同时注入）。

## 三、通信协议

**传输**：命名管道 `IPRC1000Adapter.Service`（本机、双向、字节模式）。
**帧格式**（请求/响应同构）：

```
[int32 长度 LittleEndian][utf8 JSON 字节]
```

> 为什么不用"一行 JSON"：文本协议在两个独立实现之间容易出歧义（BOM、`\r\n`、编码探测）。
> 实测就卡在 `ReadLine` 上 —— 改成长度前缀后一次通过。

**请求**：

```json
{"method":"getState","args":["",""]}
```

**响应**：`Backend.Dispatch` 的返回值（本身就是一个 JSON 对象，字段与界面 `state` 一致）。

**方法与参数**：与界面现有的 47 条命令**完全一致**（`getState` / `saveKey` / `switchGroup` / `startBridge` / `installWinuhid` …）。
参数最多两个字符串（`args[0]`、`args[1]`），与 JS 侧 `B.xxx(a, b)` 一一对应。

**错误**：业务不可达时，客户端返回

```json
{"ok":false,"message":"业务服务未运行（管道连接超时）"}
```

**超时**：连接 3 s、读 3 s。超时后**从外部关闭管道**解除阻塞 —— 不能靠 `using` 释放 reader，
否则会卡在那次未完成的读上（实测把整个调用挂死）。

### `--ui-client` 的实现要点（踩坑记录）

| 坑 | 现象 | 修法 |
|---|---|---|
| 单实例互斥 | 宿主一启动就被判"已在运行"直接退出 | `if (!createdNew && !MainForm.ClientMode)` |
| `_filter` 为空 | 宿主启动即崩（client 模式不建 KeyFilter，但 `Load` 里还在 `_filter.Start`） | 改 `_filter?.Start(...)` / `_filter?.Dispose()` |
| **端口被占** | `SocketException 10048`（UDP 31680）——`CableRouter` **在字段初始化里就绑端口** | 改为 `Start()` 里 `_udp ??= new UdpClient(...)`，不 Start 就不占端口 |
| 2 | **安装器「修复 / 复制诊断」闭环** | 见下节规格 |
| 3 | Rust 宿主（~1,300 行）| 窗口 + 托盘 + WebView2 + 管道客户端；与现 UI 行为一致 |

### 安装器闭环规格（待实现）

**入口**：安装器维护页两个按钮 —— 「修复安装」「复制诊断信息」。

**修复流程**（复用已验证的能力，不新增逻辑）：

```
① 停业务进程（若在跑）
② install-winuhid.ps1 -Mode InstallElevated -Force   ← 清空所有节点 + 重导证书 + 重建唯一节点
③ 校验 \\.\WinUHid 可打开
④ 校验桥进程能起（ETW 会话）
⑤ 结果分三级：已修复 / 需重启 / 失败（附诊断）
```

**诊断采集**（一条命令，输出可直接粘贴）：

```
install-winuhid.ps1 -Mode Status
```

含：OS 版本、管理员、证书双存储命中、设备节点 + ProblemCode、`\\.\WinUHid` 可达、WudfRd/WUDFHost、
SecureBoot/HVCI、`install.log` 尾部 20 行。

**导出格式**：纯文本（UTF-8），文件名 `IPRC1000-diag-<yyyyMMdd-HHmmss>.txt`，
默认保存到桌面，并**同时复制到剪贴板**。

**用户反馈**：按钮下方状态行显示「进行中 → 完成/需重启/失败」，失败时给"复制诊断"的引导。

## 六、已知差异与风险

| 项 | 说明 |
|---|---|
| 无 `WM_DEVICECHANGE` | `--headless` 没有窗口，收不到"设备拔出"即时事件；卡键兜底仍由看门狗负责（语音 600 s / 其它 15 s）|
| 双进程权限 | 业务需要管理员（ETW + 注入），宿主可降权运行；**当前两者都以管理员运行**，未做降权验证 |
| 端口占用 | 业务独占 UDP 31680/31681；两个业务进程会争端口，靠单实例互斥挡住 |
| 日志 | 业务进程的 stdout 必须重定向到文件（桥会持续打 `[STAT]`，不重定向会**阻塞**在管道写满）|
